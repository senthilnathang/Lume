Lume NestJS local service

Service: lume-nestjs.service (systemd user service for sibin)
Endpoint: http://127.0.0.1:3000/api/v2/health
GraphQL: http://127.0.0.1:3000/api/v2/graphql
Backend: /opt/Lume/apps/api

The service renders the actual Node executable path at installation. The system
/usr/bin/node is too old on this host; render-service.cjs requires Node 22.12+.
The .env file is loaded by Node before application imports. Secrets are not
copied into the unit. NODE_ENV=production, HOST=127.0.0.1 and PORT=3000 are set
by the unit. Both AUTOMATION_WORKER_ENABLED and AUTOMATION_DURABLE_EVENTS are
true. Email, push and AI remain unconfigured as requested.

Installation/redeployment (run as the service owner from the backend directory):
  pnpm run build
  node scripts/render-service.cjs > /tmp/lume-nestjs.service
  systemd-analyze --user verify /tmp/lume-nestjs.service
  install -d -m 700 ~/.config/systemd/user
  install -m 644 /tmp/lume-nestjs.service ~/.config/systemd/user/lume-nestjs.service
  systemctl --user daemon-reload
  loginctl enable-linger sibin
  systemctl --user enable --now lume-nestjs.service

Operations:
  systemctl --user status lume-nestjs.service
  journalctl --user -u lume-nestjs.service -n 100 --no-pager
  systemctl --user restart lume-nestjs.service
  systemctl --user stop lume-nestjs.service
  systemctl --user disable lume-nestjs.service

Nest shutdown hooks handle SIGTERM; the automation worker stops polling and
awaits its active job. systemd restarts unexpected process exits after 5 seconds
and allows up to 90 seconds for graceful shutdown. Linger keeps the user manager
running after logout and permits the enabled service to start at boot. A reboot
is not required for installation.

The service listens only on loopback. Exposing it through a public domain/reverse
proxy is a separate deployment choice. The canonical service working directory is apps/api. Root PM2 and Docker templates
also use this directory; do not run them alongside the service on the same port.

Before schema changes, create and verify a backup; never replay the entire legacy
migration sequence blindly. The current local ledger contains migrations 001–016.
Migration details and the verified backup are in docs/verification-2026-10-23.txt
at the repository root. Application rollback uses a known-good code/build and a
service restart; database rollback requires a separately reviewed recovery plan
that preserves writes made after the backup.
